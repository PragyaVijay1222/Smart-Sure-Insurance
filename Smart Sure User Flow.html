Flow 02

Policy Browse & Purchase

Covers browsing the public policy catalog, calculating a premium quote, and completing a policy purchase with full validation and event publishing.

Key Validations: Duplicate policy for same type · Coverage exceeding maximum limit · Purchasing against an INACTIVE policy type — all raise domain exceptions.
FLOWCHART 
flowchart TD
    A([Customer on Dashboard]) --> B[Browse policy-types public no auth needed]
    B --> C[GET /api/policy-types to PolicyService]
    C --> D[Display catalog cards HEALTH AUTO HOME LIFE TRAVEL BUSINESS]
    D --> E[Click Get Quote on a card]
    E --> F[Enter coverageAmount paymentFrequency age]
    F --> G[POST /api/policies/calculate-premium to PremiumCalculator]
    G --> H[Show breakdown basePremium to calculatedPremium with frequency discount]
    H --> I{Proceed to purchase?}
    I -- No --> D
    I -- Yes --> J{Authenticated?}
    J -- No --> K[authGuard redirects to auth/login with returnUrl saved]
    K --> L[Login then return to purchase]
    L --> M
    J -- Yes --> M[Fill startDate nomineeName nomineeRelation remarks]
    M --> N[POST /api/policies/purchase to PolicyService]
    N --> O{Validation}
    O -- Duplicate policy for same type --> P[Error: DuplicatePolicyException]
    O -- Coverage exceeds max --> Q[Error: CoverageExceedsLimitException]
    O -- PolicyType INACTIVE --> R[Error: InactivePolicyTypeException]
    O -- Pass --> S[Create Policy record and generate policyNumber]
    S --> T[Generate Premium Schedule installments by frequency]
    T --> U[Publish PolicyPurchasedEvent to RabbitMQ for email]
    U --> V[Save AuditLog PURCHASED]
    V --> W[Return PolicyResponse]
    W --> X[Navigate to policies id and show success toast]

Flow 03

Premium Payment — Razorpay SAGA

Details the choreography-based SAGA pattern: PolicyService initiates a Razorpay order via Feign, the frontend opens the checkout popup, and the outcome propagates back through RabbitMQ topic events.

SAGA FLOWCHART 
flowchart TD
    A([Customer on policies page]) --> B[View policy detail GET /api/policies/id]
    B --> C[See Premiums list PENDING OVERDUE PAID]
    C --> D[Click Pay Premium on a due installment]
    D --> E[Select payment method UPI CARD NET BANKING]
    E --> F[POST /api/policies/premiums/pay to PolicyService]
    F --> G{Validate: policy owner and premium not already paid?}
    G -- Fail --> H[Error: Unauthorised or Already Paid]
    G -- Pass --> I[Set Premium status to PAYMENT IN PROGRESS]
    I --> J[Feign POST /api/payments/initiate to PaymentService]
    J --> K[PaymentService creates Razorpay Order]
    K --> L[Return razorpayOrderId and razorpayKeyId]
    L --> M[Frontend opens Razorpay Checkout popup]
    M --> N{User action}
    N -- Pays successfully --> O[Razorpay callback with orderId paymentId signature]
    O --> P[POST /api/payments/confirm to PaymentService]
    P --> Q[Verify Razorpay signature]
    Q --> R[Mark Payment SUCCESS and store encrypted paymentId]
    R --> S[Publish payment.completed to smartsure.exchange topic]
    S --> T[PolicyService PaymentSagaListener receives event]
    T --> U[Update Premium to PAID and set paidDate paymentReference]
    U --> V[Fetch customer profile via Feign to AuthService]
    V --> W[Publish PremiumPaidEvent for email notification]
    W --> X[Show Payment Successful toast and update premium list]
    N -- Dismisses or Fails --> Y[POST /api/payments/fail to PaymentService]
    Y --> Z[Mark Payment as FAILED]
    Z --> AA[Publish payment.failed to smartsure.exchange topic]
    AA --> AB[PolicyService PaymentSagaListener receives event]
    AB --> AC[Update Premium to FAILED]
    AC --> AD[Show Payment Failed toast]

Flow 06

Token Lifecycle & Silent Refresh

Describes how the Angular SPA manages JWT lifecycle on boot, via the periodic monitor interval, and per-request through the auth interceptor — including automatic silent re-login using credentials stored in sessionStorage.

FLOWCHART 
flowchart TD
    A([App boots]) --> B[loadStoredUser and check localStorage for JWT]
    B --> C{JWT exists?}
    C -- No --> D[currentUser = null unauthenticated state]
    C -- Yes --> E{JWT valid and not expired?}
    E -- Yes --> F[Restore auth state and start token monitor interval]
    E -- No --> G[silentRefresh and read credentials from sessionStorage]
    G --> H{Credentials stored?}
    H -- No --> I[clearAuth and redirect to auth/login]
    H -- Yes --> J[POST /api/auth/login silent invisible to user]
    J --> K{Success?}
    K -- Yes --> L[Store new JWT and update NgRx state and restart monitor]
    K -- No --> I
    F --> M[setInterval every tokenCheckInterval ms]
    M --> N{Token expiring within threshold?}
    N -- No --> M
    N -- Yes --> O[silentRefresh]
    O --> P{Success?}
    P -- Yes --> M
    P -- No --> Q[logout and clearAuth and redirect to auth/login]
    R([Any HTTP request via authInterceptor]) --> S{Token expiring soon?}
    S -- Yes --> T[silentRefresh first then attach fresh token]
    S -- No --> U[Attach Bearer token to Authorization header]

Flow 07

Policy Lifecycle — State Diagram

All possible policy status transitions from initial creation through scheduled expiry, customer/admin cancellation, or admin discontinuation of the underlying policy type.

CREATED: Premium schedule is generated; all premiums start as PENDING.

CANCELLED: Pending premiums are WAIVED; cancellation reason stored; notification email sent; AuditLog created.

EXPIRED: AuditLog written as SYSTEM / EXPIRED; expiry reminder email sent 30 days before.
STATE DIAGRAM 
stateDiagram-v2
    [*] --> CREATED : Customer purchases with future start date
    [*] --> ACTIVE : Customer purchases with start date today
    CREATED --> ACTIVE : Start date arrives or admin overrides
    ACTIVE --> EXPIRED : Daily cron when end date passed
    ACTIVE --> CANCELLED : Customer or admin cancels
    ACTIVE --> DISCONTINUED : Admin discontinues policy type
    EXPIRED --> [*]
    CANCELLED --> [*]
    DISCONTINUED --> [*]
Flow 08

Claim Status State Machine

Transitions enforced at enum level via Status.moveTo() — invalid transitions throw InvalidStatusTransitionException. All terminal paths converge at CLOSED.

DRAFT: Customer can upload Claim Form, Aadhaar Card, and Evidence docs.

UNDER_REVIEW: Admin can download all uploaded files. X-Admin-Id header is required for all admin actions.
STATE DIAGRAM 
stateDiagram-v2
    [*] --> DRAFT : Customer creates claim via POST /api/claims
    DRAFT --> SUBMITTED : Customer submits via PUT /claims/id/submit
    SUBMITTED --> UNDER_REVIEW : Admin marks for review
    UNDER_REVIEW --> APPROVED : Admin approves
    UNDER_REVIEW --> REJECTED : Admin rejects
    APPROVED --> CLOSED : Admin closes
    REJECTED --> CLOSED : Admin closes
    CLOSED --> [*]
